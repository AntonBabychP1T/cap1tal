# goals-scope-and-caps — design

## Context

See [proposal.md](proposal.md) — Why. What matters here is what already exists and constrains the
shape of the answer:

- `domain/goals.ts` holds `Goal { id, name, target, deadline, accountId }` and three functions:
  `goalProgress` (delegates to `computeBalance`), `isReached`, `isOverdue`. The domain is
  **rate-free** by rule — no conversion lives in `src/domain`.
- `domain/limits.ts` holds `CategoryLimit { categoryId, amount }`, `overLimit`, `overLimitBy` and
  `overLimitCategories`, all reading `monthly-picture`'s `categoryBreakdown` — витрати minus
  повернення per category per currency, negative коригування under the correction category.
- `ui/approx-uah.ts` holds the only conversion in the app: `approximateUah(amount, rateMillionths)`
  in BigInt with halves away from zero, and `approximatePicture`, whose rule is «one unknown rate
  withholds the whole approximation». monobank rates are **UAH per one unit of a currency**
  (`monobank_rates.rate_millionths`), so UAH is the only currency the app can convert *into*.
- Storage: `goals(id, name, amount, currency, deadline NOT NULL, account_id NOT NULL → accounts)`
  and `category_limits(category_id PK → categories, amount, currency)`.
  **Migration numbering is a moving target while other changes are in flight, so no number here is
  a number to copy.** At the commit this change was written against there were thirteen committed
  migrations (`0000`–`0012`) and `BACKUP_SCHEMA_VERSION = 13`; the working tree this change is
  implemented in also carries `0013` and `0014` — `monobank-auto-sync`'s and `bug-report-here`'s,
  generated but not yet committed — so `drizzle/meta/_journal.json` has fifteen entries and
  `src/backup/format.ts` already reads `BACKUP_SCHEMA_VERSION = 15`. `BACKUP_FORMAT_VERSION = 1`.
  What section 3 depends on is the *shape* — `goals` still holds one `account_id` and a
  `NOT NULL` deadline, and no `goal_accounts` exists — not the indices.
- Migration rules (`.claude/rules/database.md`): committed migrations are immutable; DDL is
  generated by `npm run db:generate`, never hand-written; **data** statements may be hand-added to
  an uncommitted migration when the schema change cannot land without them, with a comment saying
  why and a test that fails without it; the migrator runs inside its own `BEGIN`, which makes
  drizzle's generated `PRAGMA foreign_keys=OFF` a **no-op** — foreign keys are enforced throughout
  a migration.
- `investments-value` is written but not implemented (0/12 tasks). It introduces one hand-entered
  **поточна вартість** per інвестиційний рахунок, in that рахунок's own currency.

## Goals / Non-Goals

**Goals**

- One stored truth per number: a ціль витрат reads and writes the `category_limits` row; a
  ціль-накопичення reads балансі and вартості that already exist.
- The domain stays rate-free and pure; conversion stays in `src/ui`, where `approx-uah.ts` already
  is, and `npm run verify` stays Node-only.
- Existing цілі survive with byte-identical progress, and no committed migration is touched.
- A progress that cannot be counted honestly is absent, never partial and never zero.

**Non-Goals (design level)**

- No cross-currency rate arithmetic (D5), no rate history, no per-ціль rate snapshot.
- No stored progress, no stored conversion, no cache of either — everything is computed at read
  time from балансі, вартості and the rate table, exactly as today.
- No change to `monthly-picture`, `reports`, `accounts` or `money`.

## Decisions

### D1. A ціль витрат **is** the `category_limits` row — no new table, no new column

The owner's brief asks that a ціль витрат and a ліміт cannot hold two different target amounts. The only way to make that structurally impossible rather than merely enforced is for there
to be one row. So:

- `goals` holds **only** цілі-накопичення. It gains no `kind` column, because a `kind` column would
  only ever hold one value.
- The «Цілі» list is a **union built in `src/ui`**: `goalRows(goals)` ∪ `spendingGoalRows(limits,
  categories, breakdown)`. Nothing in `src/db` or `src/domain` knows about that union.
- The ціль витрат's identity is its `categoryId`; its назва is the категорія's назва; its period is
  the calendar month, which is what a ліміт already is.
- Creating one is `limitsRepo.set`; deleting one is `limitsRepo.clear`.

*Alternative rejected*: a `goals.kind` discriminator with a nullable `category_id` and a nullable
`amount` that shadows the ліміт. It gives a uniform list at the price of two ceilings per категорія
and a rule («keep them in sync») that only code can hold. The rule this repo follows for progress —
«never a second number that could drift from the stored truth» — says the same about a ceiling.

*Consequence, accepted*: **every** ліміт shows up among the цілі. The owner has two entry points to
one row, so «Ліміти» stays where it is and gains a sentence saying the two are one thing. Hiding
some ліміти from the цілі would need a flag, and a flag is the first half of a second truth.

### D2. The склад is a stored set of account ids; kind shortcuts are UI, not model

Requested explicitly in the brief: shortcuts must not be ambiguous. A dynamic scope («all
investment accounts, as of now») makes a ціль change its meaning when an unrelated рахунок is
created, and makes an archived рахунок silently leave a ціль — the brief forbids both. So the
shortcut is a **multi-select convenience**: it ticks the boxes for the рахунки of that вид at the
moment it is tapped, and what is stored is the ticked ids.

Storage is a join table, per the brief and per `.claude/rules/database.md` (unstructured JSON is
not how this schema stores a relation):

```
goal_accounts(
  goal_id   TEXT NOT NULL REFERENCES goals(id)    ON DELETE CASCADE,
  account_id TEXT NOT NULL REFERENCES accounts(id) ON DELETE RESTRICT,
  PRIMARY KEY (goal_id, account_id)
)
```

The composite primary key **is** «no рахунок twice», a property of the shape rather than of a check.
A склад naming one рахунок twice is refused by the repository rather than quietly deduplicated:
the form ticks boxes and cannot produce a duplicate, so a duplicate arriving at storage is a bug
and is treated as one. `ON DELETE CASCADE` on `goal_id` because a склад row has no meaning without
its ціль; `ON DELETE RESTRICT` on `account_id` like every other reference to a рахунок (рахунки are
archived, never deleted).

### D3. `goals` loses `account_id`; `deadline` becomes nullable

A ціль-накопичення has no «primary» рахунок, so keeping `account_id` would leave a column that
contradicts the model. The дата becomes optional because the brief asks for «дата — якщо потрібна»,
and because a nullable column is the only honest way to say «this ціль has no deadline» — a
sentinel date would be a lie every screen would have to un-tell.

The resulting shape:

```
goals(id PK, name NOT NULL, amount NOT NULL, currency NOT NULL, deadline NULL)
  CHECK amount > 0
  CHECK length(trim(name)) > 0
  CHECK deadline IS NULL OR deadline GLOB '[0-9][0-9][0-9][0-9]-[0-9][0-9]-[0-9][0-9]'
```

The `currency` column stays and is now genuinely the ціль's own — the old repo invariant «equal to
the рахунок's currency» is replaced by D5's rule, checked in `goals-repo` the same way (a
read-and-compare in the one writer, since SQLite cannot express it).

### D4. Two migrations, one hand-added data statement — because foreign keys are on

Foreign keys are enforced during a migration (see Context), and drizzle's only way to change a
SQLite column is to rebuild the table: `CREATE __new_goals` → `INSERT … SELECT` → **`DROP TABLE
goals`** → `RENAME`. `DROP TABLE` with foreign keys on performs an implicit `DELETE FROM`, so it
fails if `goal_accounts` already holds rows pointing at `goals` — and `ON DELETE CASCADE` would be
worse than failing: it would silently delete the склад rows we just copied.

The copy must therefore happen **before** the drop, into a table that does not yet reference
`goals`. Hence two migrations, both new:

1. **The first** (whichever number `db:generate` emits in the tree it is run in — `0015` in the
   tree this change was implemented in, and not a number to copy) — `CREATE TABLE goal_accounts` with `goal_id TEXT NOT NULL` **and no foreign key on
   it yet** (the `account_id` foreign key is there from the start), then the one hand-added data
   statement, then the generated rebuild of `goals`:

   ```sql
   -- Data, hand-added: every stored ціль names exactly one рахунок, and this is the only moment
   -- that pairing still exists — the rebuild of `goals` below drops the account_id column with the
   -- table. goal_accounts carries no foreign key to goals in this migration precisely so that it
   -- may already hold rows while `goals` is dropped (foreign keys are on: the generated
   -- PRAGMA foreign_keys=OFF is a no-op inside the migrator's own BEGIN).
   INSERT INTO goal_accounts (goal_id, account_id) SELECT id, account_id FROM goals;
   ```

2. **The second** — generated from `schema.ts` once the `goal_id → goals(id)` reference is added:
   a rebuild of `goal_accounts` that copies its rows and lands the foreign key. Nothing references
   `goal_accounts`, so dropping it in a rebuild is safe, and by now the rows point at a stable
   `goals` table.

**Precondition.** These two migrations are generated in a tree that already carries every other
in-flight change's migrations, and their numbers are read from `_journal.json` after generating,
never assumed. Generating them in a lane where another change's untracked migration is absent would
emit the same index that lane will emit, and the two would collide by filename and by journal index
when the lanes meet. For the same reason `migrations.test.ts` seeds its pre-migration database by
**index** — `openTestDbMigratedTo(n)` where `n` is the journal length immediately before this
change's first migration — and not by a tag written into this document.

The implementer must **verify the emitted statement order in the first migration** (the
`CREATE TABLE goal_accounts` must precede the `goals` rebuild; drizzle-kit emits created tables first, but this
is checked, not assumed) and must place the `INSERT` between them. `migrations.test.ts` gets a case
that seeds a database built by the previously committed migrations with two цілі and asserts the склад after migrating — it fails
without the hand-added statement, which is exactly the test `.claude/rules/database.md` demands.

*Alternative rejected*: one migration with a hand-written `CREATE TEMP TABLE … AS SELECT` carrier.
It is one migration instead of two, but it hand-writes DDL, which the rules forbid outright.

*Alternative rejected*: leaving `account_id` on `goals` as a nullable vestige. No rebuild, no
ordering problem — and a dead column that contradicts the model forever.

### D5. A ціль's currency is UAH, or the one currency its склад shares

monobank quotes **UAH per unit**; there is no rate table entry that converts EUR into USD. Getting
one means dividing two rates, which introduces a second rounding, a direction question (buy or
sell, twice) and a number no one can check against a bank screen. For v1 the app converts into UAH
and nothing else, so:

- склад of one currency → the ціль may be in that currency (exact, no conversion) **or** in UAH
  (converted, approximate);
- склад of several currencies → the ціль must be in UAH.

Checked in three places for three different reasons: in `ui/goals-section.ts` so the owner is
refused in Ukrainian while typing; in `db/goals-repo.ts` so the invariant is not representable in
storage; in `backup/format.ts` so a hand-edited бекап cannot smuggle one in.

*Alternative rejected*: cross rates via UAH. It is the obvious extension and it is a separate
change — it needs its own decision about rounding and about what «≈» means twice over.

### D6. Progress is computed in `src/ui`, over a value the domain produced

The domain must stay rate-free, and progress needs rates. So the split is:

- `src/domain/goals.ts` — pure, rate-free: `AccumulationGoal { id, name, target, deadline?,
  accountIds }`, `contribution(account, transactions, currentValue?)`, `isReached`, `isOverdue`,
  and the spending side as a thin reading of `limits.ts` (`SpendingGoalState` from `overLimit` /
  `overLimitBy`) — no new spending arithmetic anywhere.
- `src/ui/goal-progress.ts` (new) — takes the внески, the ціль's currency and the stored rates and
  returns a discriminated result:
  `{ kind: 'exact' | 'approximate', total, parts } | { kind: 'unknown', missingCurrencies, parts }`.
  It uses `approximateUah` verbatim: same BigInt, same halves-away-from-zero, same rate, same
  direction. It rounds **per внесок**, before the sum, because the breakdown screen lists the
  внески and they have to add up to the total above them. `approximatePicture` rounds once per
  currency total instead, so two USD рахунки in one ціль can land a minor unit away from the
  Місяць tab's figure for the same money. That is accepted and stated in the spec: both are marked
  приблизний, and the per-currency amounts neither of them touches are the truth.
- `src/ui/goal-screen.ts` and the ціль rows of `reports-screen.ts` render that result; neither
  invents a fallback when it is `unknown`.

The `unknown` case covers a missing rate **and** a sum that leaves the safe-integer range — the same
two reasons `approximatePicture` returns `null` today. Because it is a discriminated union rather
than a nullable number, «no progress» cannot be mistaken for «progress of zero» at a call site.

### D7. The внесок of an інвестиційний рахунок, before and after `investments-value`

`contribution` takes the поточна вартість as an **optional argument**, not as a lookup:

```
contribution(account, transactions, currentValue?) =
  account.kind === 'investment' && currentValue !== undefined
    ? currentValue
    : computeBalance(account, transactions)
```

The дата a вартість carries is **not** part of `contribution` — the domain computes a сума, and a
дата is not one. It travels beside it to the view models that show it: `goal-screen` states the
вартість's дата, so its input carries the вартість **and** its дата, while `goal-progress` and
`src/analysis` take the сума alone.

The test is **presence, not truthiness**: `investments-value` explicitly accepts a вартість of 0
(«an інвестиція can be worth nothing, never less than nothing»), and a truthy test would silently
fall back to the розрахунковий баланс for exactly the рахунок whose worth the owner has just said
is nothing.

Today no вартість exists, the argument is always absent, and an інвестиційний рахунок contributes
its розрахунковий баланс — which is its вкладено, the number `investments-value` itself defines. The
day `investments-value` lands, the screens pass what its repo returns and nothing in `goals` changes.
This makes the two changes independent in either order, and it is what keeps the app from ever
holding a second «вартість для цілі».

### D8. Percentage: one rule, floor, and never 100 % before it is true

`floor(part × 100 / whole)` on integers, clamped at 0 for a negative numerator. Floor is what keeps
«99 %» honest — a ціль at 69 999 999 of 70 000 000 must not read 100 % — and it makes «100 %» mean
exactly «reached» for a ціль-накопичення and exactly «the ceiling is used up, and not exceeded» for
a ціль витрат, since equality is not over (the ліміт's own rule). Once a ціль витрат is exceeded
there is **no percentage at all**, so no number above 100 is ever produced for it.

The whole progress line, the percentage and the remainder are produced by one pure function per
kind, in `src/ui`, so the two vocabularies cannot leak into one another: a ціль-накопичення's row
model has `leftToAccumulate` and `reached`; a ціль витрат's has `mayStillSpend`, `exceededBy` and
`monthLabel`, and neither type has the other's fields. The type system is the guard the brief asks
for in §6.

### D9. The ціль витрат's month, and what «final» means

The row on «Звіти» is always about the **current** calendar month, read from the same
`categoryBreakdown` the Місяць tab and the ліміт read. The state is a total function of three
inputs — the month's spent, the ceiling, and whether the month has ended — in that order: over the
ceiling is `exceeded` whether the month ended or not; otherwise an ended month is
`завершено в межах` and a running one is `within`. A month that has not begun is asked about
nowhere and has no state at all, which is why the function is offered a *boolean* «has ended» and
not a tri-state: the caller only ever asks about a month that exists. A month that has ended has
one verdict — `завершено в межах` or `перевищено на X` — decided by that month's транзакції alone. «Final» is
therefore «final unless that month's транзакції change», which is the same sentence every other
monthly number in this app obeys; the spec says it that way rather than promising an immutability
the data model does not have.

Choosing a ціль витрат navigates to the existing `category/[month]/[categoryId]` route with the
month it was shown for. No new list, per the brief.

### D10. Backup: format version 2, a new schema version, and a reader for version 1

`BackupState.goals` changes shape (`accountId` → `accountIds: string[]`, `deadline` optional), and a
shape change inside a list is not covered by the existing «an older бекап simply names fewer
things» rule. So `BACKUP_FORMAT_VERSION` goes to **2**, and `goalAt` accepts both:

- a value carrying `accountIds` → used as the склад;
- a value carrying `accountId` (a version-1 file) → a склад of that one рахунок.

`BACKUP_SCHEMA_VERSION` becomes the length of `drizzle/meta/_journal.json` after both migrations —
two more than whatever it is when this change starts, and not a number to copy from here, since
`investments-value` and `achievements-and-financial-challenges` are in flight with migrations of
their own. `format.test.ts`'s tripwire against that journal is what forces this file to be opened
at all. `BACKUP_TABLES` gains
`goal_accounts`; the ціль витрат adds nothing, because `category_limits` is already in that list —
which is why the ціль витрат costs the бекап nothing. The Google Drive change needs no edit: it
uploads whatever file this format produces.

The self-consistency check in `format.ts` moves from «a ціль's currency equals its рахунок's» to
D5's rule, plus «every рахунок of a склад is in the бекап», «a склад is non-empty» and «a склад
names no рахунок twice».

### D11. Archived рахунки, and the picker

An archived рахунок stays in the склад, keeps contributing, and is marked «в архіві» on the
breakdown screen — the existing `goals` rule, unchanged.
The picker follows the pattern already stated once in `ui/account-choices.ts`: the unarchived
рахунки, plus whatever the ціль already holds (`withCurrent`, extended to a set). The kind
shortcuts offer only unarchived рахунки of that вид — a shortcut is a way to tick what is current,
not a way to resurrect an archive.

### D12. Screens and routes

| Route | What it is |
| --- | --- |
| `manage/goals.tsx` | kind chooser → the two forms; writes `goalsRepo` or `limitsRepo` |
| `(tabs)/reports.tsx` | two named ціль groups; each row navigates |
| `goal/[id].tsx` *(new)* | the breakdown of one ціль-накопичення |
| `category/[month]/[categoryId].tsx` | unchanged; where a ціль витрат leads |

All screen logic lives in `src/ui/*.ts` as plain TypeScript so `verify` can test it without JSX,
per CLAUDE.md. `goal/[id].tsx` is a pushed screen like `account/[id].tsx` and follows the same
back-gesture behaviour it already has.

### D13. The пакет для аналізу carries a ціль only when its progress is exact

`src/analysis/goals.ts` is shipped code with a shipped requirement, and it breaks on this change in
three ways at once: `GoalReport.deadline` is required, the progress is `goalProgress(account, …)`
over one рахунок, and «every ціль» would now include every ліміт twice over. The пакет's own
defining property decides the fix — «per currency, never mixed, every сума exact, from the stored
транзакції alone»:

- цілі витрат are **not** carried among the цілі; the пакет already carries the ліміти, and that is
  the same ceiling;
- a ціль-накопичення whose склад is entirely in the ціль's own currency is carried as it is today,
  progress and pace included — the sum needs no rate and is exact;
- a ціль-накопичення whose склад holds another currency is carried with its назва, target and дата
  and **no progress** — carrying an approximate сума would break the пакет's rule, and carrying the
  exact part would be a partial number wearing a total's name;
- a ціль with no дата is carried with no `monthsLeft` and no `perMonth`, and is never overdue.

`src/analysis` therefore needs **no rate and no dependency on `src/ui`**: «is this progress exact»
is «is every рахунок of the склад in the ціль's currency», a pure question over the stored rows.

The вартості reach it the same way they reach the screens — as an argument, from the same repo, so
the пакет's progress for a ціль is the identical number «Звіти» shows. That matters the day
`investments-value` lands and not before: until then no вартість exists anywhere and every caller
passes none. It is still «progress as the goals capability defines it», because a вартість is in its
рахунок's own currency, and the пакет carries a progress only when that currency is the ціль's.

## Risks / Trade-offs

- **The migration is the sharp edge: it rebuilds `goals` while foreign keys are on.** → Two
  migrations (D4), a hand-added data statement with a comment, and a `migrations.test.ts` case that
  seeds pre-`0014` rows and fails without it. The implementer verifies the emitted statement order
  before committing, and never edits a committed migration.
- **Every ліміт becoming visible among the цілі may feel like noise** if the owner sets many. →
  Accepted deliberately (D1): it is the price of one truth, and the two kinds are in separate,
  named groups so neither crowds the other. A later change may add a way to fold the group; a flag
  now would be the first half of a second truth.
- **A EUR ціль backed by USD рахунки is refused, not approximated** (D5). → The refusal names the
  reason and offers UAH, which the owner's own example already uses. Cross rates are a change of
  their own.
- **A missing EUR rate hides the progress of an otherwise-countable ціль, including a reached one.**
  → Deliberate, and the same rule the Місяць tab already follows. The breakdown screen still shows
  every внесок it can read, so the owner is never left with nothing; and rates refresh on their own
  within the hour `RATE_MAX_AGE_MS` allows.
- **The percentage is display arithmetic on integers and can look off by one** next to a hand
  calculation. → Floor is stated once, in one function, used by both the list and the detail, and
  tested at the boundaries (69 999 999 / 70 000 000 → 99 %, equality → 100 %).
- **`goal-screen` reads every транзакція to compute балансі**, like «Звіти» already does. → Same
  order of magnitude as the screen it is opened from; if it ever bites, the fix is a balance query
  in the repo, not a stored progress.
- **The AI-аналіз loses a number it used to carry** for a mixed-currency ціль (D13). → Deliberate:
  the alternative is an approximate сума inside a пакет whose whole contract is exactness. The
  ціль is still named with its target and дата, so the assistant knows it exists and does not
  invent a progress for it.
- **Removing `account_id` from `goals` is irreversible without a restore.** → The data it held is
  copied into `goal_accounts` in the same migration, and the migration test proves the copy for
  representative rows before anything ships.

## Migration Plan

1. `goal_accounts` and the reshaped `goals` land in the two new migrations of D4 — the numbers
   `db:generate` emits, not numbers copied from this document; committed migrations are untouched.
2. On first launch after the update, every existing ціль becomes a ціль-накопичення whose склад is
   the one рахунок it was linked to, with its назва, target, currency and дата unchanged — so its
   progress is the number it showed the day before.
3. Every existing ліміт becomes readable as a ціль витрат with no data change at all.
4. Rollback is a бекап restore, as for every other schema change here; a бекап written by the new
   version names бекап format 2 and the storage shape version D10 arrives at, and is refused by an
   older build — the intended behaviour of the version check.

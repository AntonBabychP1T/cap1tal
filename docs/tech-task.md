# cap1tal — технічне завдання (v1)

Мова документа — українська, бо це робочий документ власника. Джерела правди:
[product-vision.md](product-vision.md) (продукт і межі) та [glossary.md](glossary.md) (терміни —
вживаються тут у точних значеннях звідти). Стек зафіксовано: Expo / React Native, TypeScript,
SQLite + Drizzle ORM, npm, Android-перш (iOS не збирається, але ніщо не має йому заважати).

У міру реалізації правдою поведінки стають специфікації в `openspec/specs/`; цей документ —
вхідна мапа, а не жива спека. Розбіжність між ними — привід оновити цей файл.

## 1. Загальний вигляд

Застосунок для однієї людини з одним основним телефоном. Працює офлайн з локальною базою;
мережеві з'єднання — monobank API (транзакції, баланси, курс) з токеном власника та, лише
після явного підключення, Google Drive для резервних копій. Жодного акаунта cap1tal,
спільного доступу чи аналітики. Інші люди можуть встановити застосунок собі — нічого
персонального не зашито.

П'ять вкладок (правда про кожну — у спеці `openspec/specs/<...>-screen`):

1. **Головний** — швидке додавання транзакції, чернетки від сповіщень банків і стрічка останніх
   транзакцій. Нерозпізнані імпортовані транзакції ("Без категорії") підсвічені, категоризація в
   один тап.
2. **Місяць** — витрачено / інвестовано / відкладено / позичено / залишилось за календарний
   місяць, окремо по кожній валюті + приблизний підсумок у гривні; розбивка витрат за
   категоріями, перевищені ліміти — червоні. Місяць без доходу веде «Витрачено», а не
   «Залишилось».
3. **Рахунки** — згруповані за видами (картки, готівка, банки, інвестиційні, борги);
   розрахунковий баланс; для monobank поруч баланс банку і дія "звірити"; для інвестиційного
   рахунку — вкладено / поточна вартість / прибуток.
4. **Звіти** — витрачено/дохід/інвестовано по місяцях за весь час; категорія по місяцях;
   цілі з прогресом.
5. **Налаштування** — список розділів: «Перші кроки», Категорії, Джерела, Правила, Ліміти,
   Цілі, Імпорт Saldo, monobank, Сповіщення банків, Нагадування, Бекап (далі — Google Drive).

Над вкладками, а не поруч із ними, відкриваються: редагування транзакції, транзакції категорії
за місяць, «Перші кроки» і кожен розділ Налаштувань; зміна `daily-usability` (ще не
заархівована) додає туди ж рухи рахунку і повний список транзакцій з пошуком.

## 2. Функціональні вимоги

### FR-A. Рахунки
- FR-A1. Створення, перейменування, архівація рахунків; у кожного — вид
  (`spending` / `savings` / `investment` / `cash` / `debt`) і валюта (UAH/EUR/USD, розширювано).
- FR-A2. Баланс рахунку завжди розрахунковий: початковий залишок + усі транзакції.
  Балансів, які не пояснюються транзакціями, не існує.
- FR-A3. Для рахунків з API (monobank) поруч показується баланс банку; дія "звірити" створює
  транзакцію-коригування на різницю.
- FR-A4. Рахунок-борг створюється на людину; його баланс = скільки ця людина винна.

### FR-T. Транзакції
- FR-T1. Типи: витрата (за замовчуванням), дохід, переказ, повернення, коригування.
  Будь-яка транзакція — витрата, поки явно не типізована інакше.
- FR-T2. Витрата має категорію; дохід має джерело; сума — цілі мінорні одиниці + код валюти.
- FR-T3. Переказ з'єднує два власні рахунки; між різними валютами несе дві суми (скільки пішло /
  скільки прийшло), курс не зберігається. Переказ не входить у "витрачено".
- FR-T4. Переказ у гривнях, де прийшло менше ніж пішло, автоматично пропонує різницю як
  витрату "Комісія".
- FR-T5. Повернення = від'ємна витрата в тій самій категорії місяцем надходження. Ніколи не дохід.
- FR-T6. Коригування має власну категорію "Коригування": мінус рахується як витрачено,
  плюс — як дохід.
- FR-T7. Валютна покупка з гривневої картки: витрата — у списаних гривнях; сума в оригінальній
  валюті зберігається як довідкова.
- FR-T8. Редагування і видалення транзакцій; зміна типу (витрата → переказ/інвестиція) —
  штатна щоденна дія з головного екрана.
- FR-T9. Повернення боргу понад тіло автоматично пропонується як дохід "Відсотки".

### FR-S. Джерела транзакцій (у порядку пріоритету)
- FR-S1. Ручне додавання — з головного екрана, мінімум полів: сума, рахунок, категорія.
- FR-S2. monobank API: підтягування нових транзакцій по всіх картках і банках токена,
  без дублів, з балансами. Токен зберігається лише на пристрої.
- FR-S3. Push-сповіщення інших банківських застосунків фізично читаються нативним Android
  `NotificationListenerService` після явного системного дозволу і передаються через platform-
  адаптер у локальний parser. Відстежуваний застосунок прив'язаний до одного рахунку; прочитане
  атомарно стає fingerprint + чернеткою або автоматично підтвердженою витратою за правилом.
  Повторна доставка не створює дубль, нерозпізнаний формат не губиться, а сирі payload-и не
  покидають пристрій.
- FR-S4. Разовий CSV-імпорт історії з експорту Saldo (див. FR-X).

### FR-C. Категорії, джерела доходу, правила
- FR-C1. Плоский список категорій витрат і джерел доходу, редагований; стартовий набір —
  категорії власника з Saldo (ієрархія доходів сплющується).
- FR-C2. Правила автокатегоризації "продавець/MCC → категорія", редаговані; застосовуються до
  імпортованих транзакцій (FR-S2–S4).
- FR-C3. Нерозпізнане потрапляє в "Без категорії", рахується як витрачено, підсвічується на
  головному; категоризація звідти — в один тап, з пропозицією створити правило.

### FR-M. Місячна картина
- FR-M1. Період — календарний місяць.
- FR-M2. За місяць і по кожній валюті окремо: **витрачено** (витрати мінус повернення, включно з
  "Без категорії", коригуваннями-мінус і комісіями), **інвестовано** (нетто переказів на
  інвестиційні рахунки; повернення зменшують, може бути від'ємним), **відкладено** (нетто в
  savings), **позичено** (нетто в debt), **дохід**, **залишилось** = дохід − витрачено −
  інвестовано − відкладено − позичено.
- FR-M3. Поруч — приблизний підсумок у гривні за поточним курсом monobank, позначений як
  приблизний; первинні числа — по валютах.
- FR-M4. Розбивка витрат за категоріями за місяць; перехід до транзакцій категорії.

### FR-L. Ліміти
- FR-L1. Необов'язковий місячний ліміт на категорію.
- FR-L2. Перевищення показується червоним у місячній картині і в списку транзакцій.
  Окремого сповіщення про перевищення немає, нічого не блокується.

### FR-R. Звіти і цілі
- FR-R1. Графік витрачено / дохід / інвестовано по місяцях за всю історію.
- FR-R2. Графік однієї категорії по місяцях.
- FR-R3. Цілі "відкласти N до дати" з прогресом. Вирішено у `limits-goals-reports`: ціль
  прив'язана до одного рахунку, а її прогрес — розрахунковий баланс цього рахунку, ніколи не
  друге число, введене рукою. Ціль у валюті свого рахунку, нічого не конвертується.

### FR-I. Інвестиції
- FR-I1. Інвестиція = переказ на рахунок виду `investment`; "вкладено" рахунку = нетто цих
  переказів.
- FR-I2. Власник вручну вводить поточну вартість рахунку; застосунок показує прибуток/збиток
  проти вкладеного. Позиції, інструменти, автоціни — поза v1.

### FR-B. Бекап
- FR-B1. Експорт повного стану (рахунки, категорії, правила, ліміти, цілі, транзакції,
  налаштування без секретів) в один файл; імпорт цього файлу на чистій інсталяції відновлює все.
- FR-B2. monobank-токен у бекап не потрапляє.
- FR-B3. Власник може опційно підключити Google Drive. Принаймні раз на 24 години застосунок
  best-effort завантажує туди актуальний бекап, а пропущену системою фонову роботу надолужує
  при наступному відкритті. Є ручні «Зберегти зараз» і «Відновити», дата останнього успіху,
  помилка з повтором і невелика ротація версій. Це резервна копія одного телефона, не live-sync.
- FR-B4. Drive-бекап не містить monobank-токена, Google OAuth-секретів, сирих payload-ів
  банківських сповіщень або локальної capture-черги; цілісність, версія схеми та контракт
  шифрування перевіряються до заміни локальної бази.

### FR-N. Нагадування і службові сповіщення
- FR-N1. Опційне локальне нагадування «Записати й перевірити витрати» надсилається раз на день
  у час, який обрав власник. Тап відкриває Головний і pending-чернетки; час можна змінити,
  нагадування — вимкнути.
- FR-N2. Помилка, що потребує дії (імпорт, локальне збереження, файловий або Drive-бекап,
  читання/обробка банківських сповіщень), може створити локальне системне сповіщення з переходом
  до деталей і повтору. Одна помилка не дублюється, секрети й банківський текст на lock screen
  не показуються.
- FR-N3. Для FR-N1–N2 не потрібен зовнішній push-сервер: це локальні notifications застосунку.

### FR-X. Імпорт Saldo (разовий)
- FR-X1. Читає експортний CSV Saldo (подвійний запис: дві ноги на транзакцію).
- FR-X2. Ручні і авто-дублі однієї картки ("mono black" ↔ "Monobank UAH, Black" тощо)
  зливаються в один рахунок за мапою, яку користувач підтверджує перед імпортом.
- FR-X3. Історія категорії "Борг" мапиться на рахунки-борги (позика = переказ туди, повернення =
  переказ назад); усі імпортовані борги закриті — вони лягають на один рахунок-борг "Борги" на
  кожну валюту, особа не зберігається, опис транзакції для цього не читається.
- FR-X4. MONEY_ON_THE_WAY-записи Saldo згортаються у звичайні перекази; трьохногі транзакції
  (комісія) імпортуються як переказ + витрата "Комісія".
- FR-X5. Після імпорту розрахункові баланси збігаються з балансами в Saldo на момент експорту;
  розбіжності показуються списком до підтвердження.

## 3. Нефункціональні вимоги
- Офлайн-перш: усе працює без мережі, крім синку mono, курсу і опційного Drive-бекапу.
- Приватність: локальна БД є первинною; жодної телеметрії; банківські сповіщення розбираються
  локально. У Google Drive іде лише явно ввімкнений бекап за FR-B3–B4.
- Гроші: цілі мінорні одиниці скрізь, від БД до UI; float заборонено.
- Швидкість: додавання транзакції — без відчутної затримки; місячна картина на історії
  ~5 тис. транзакцій — до секунди.
- Мова інтерфейсу — українська (терміни з глосарію).
- Ніяких Android-припущень у доменному і БД-коді; платформозалежне — за одним адаптером.

## 4. Поза межами v1
Повний список — [product-vision.md §14](product-vision.md). Коротко: без live-sync і акаунтів, без
позицій/автоцін інвестицій, без дат і ставок боргів, без розбиття покупки на категорії, без
регулярних транзакцій, без інших інтеграцій (тільки mono API + сповіщення), без ієрархії
категорій і тегів, без хмарних сервісів крім опційного Google Drive бекапу, без прогнозів,
без переносу транзакцій між місяцями, без платежів із застосунку, без загального ліміту,
без віддалених push-сповіщень, без iOS-збірки.

## 5. Подальші кроки

`/opsx:propose` → `spec-reviewer` → `/opsx:apply` → `npm run verify` → `diff-reviewer` → коміт →
`/opsx:archive`. Порядок нижче — орієнтир; правда про стан — `openspec list`.

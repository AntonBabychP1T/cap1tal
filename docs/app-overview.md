## 1. Що це за застосунок

Персональний облік грошей для однієї людини з одним основним телефоном. Два питання, на які він
має відповідати (§1 візії):

- **«Куди пішли гроші цього місяця?»**
- **«Скільки я ще можу витратити?»**

Працює офлайн з локальною базою SQLite. Назовні йдуть лише запити до monobank API з токеном
власника (транзакції, баланси, курс). Жодного акаунта cap1tal, спільного доступу, аналітики чи
серверної частини. Інші люди можуть встановити застосунок собі — нічого персонального не зашито.

Стек зафіксовано і не переглядається: Expo / React Native, TypeScript, SQLite + Drizzle ORM, npm,
Android-перш (iOS не збирається, але ніщо в моделі не має йому заважати).

## 2. Словник у двох словах

Повний словник — [glossary.md](glossary.md); тут лише те, без чого не читаються скріншоти.

| Термін | Що це |
|---|---|
| **рахунок** | місце, де лежать гроші: картка, банка, готівка, інвестиційний рахунок, борг людини |
| **вид рахунку** | `spending` / `savings` / `investment` / `cash` / `debt` — вирішує, як переказ **на** цей рахунок рахується в місяці |
| **транзакція** | один рух грошей: **витрата** (за замовчуванням), **дохід**, **переказ**, **повернення**, **коригування** |
| **категорія** / **джерело** | мітка витрати / мітка доходу; плоскі списки власника |
| **правило** | «продавець або MCC → категорія», застосовується до імпорту |
| **ліміт** | місячна стеля по категорії; перевищення — червоне, нічого не блокує |
| **ціль** | «відкласти N до дати»; прогрес = розрахунковий баланс прив'язаного рахунку |
| **чернетка** | запропонована транзакція, про яку власник ще не сказав ні слова; грошей не рухає |
| **місячна картина** | витрачено / інвестовано / відкладено / позичено / дохід / **залишилось** за календарний місяць |

Головна формула місяця:

```
залишилось = дохід − витрачено − інвестовано − відкладено − позичено
```

Гроші, покладені в банку або позичені комусь, не виглядають доступними — у цьому й сенс.
Усі числа рахуються **окремо по кожній валюті**; приблизна гривня — вторинна і лише для показу.

## 3. Екрани

П'ять вкладок у порядку, у якому їх називає технічне завдання: **Головний**, **Місяць**,
**Рахунки**, **Звіти**, **Налаштування**. Усе інше — екрани, що виїжджають поверх вкладок
(`Stack` у [_layout.tsx](../src/app/_layout.tsx)), а не шості вкладки.

### 3.1. Перший запуск

<img src="screens/00-splash.png" width="260"> <img src="screens/01-onboarding.png" width="260"> <img src="screens/02-onboarding-progress.png" width="260">

Пристрій, на якому ще нічого немає, відкривається на «Перші кроки»
([onboarding.tsx](../src/app/onboarding.tsx)). Екран **нічого не пише в базу** — він лише називає
стан кожного кроку і веде на екран, який цей стан змінює:

1. **Рахунки** — без жодного рахунку записати транзакцію нема куди.
2. **Історія з Saldo** — разовий імпорт, необов'язковий.
3. **monobank** — токен і зв'язування рахунків.
4. **Сповіщення банків** — дозвіл пояснюється **до** того, як його просять.

Праворуч — той самий екран після імпорту: «Готово 2/4». Пізніше він доступний з
«Налаштування → Перші кроки».

### 3.2. Головний — стан місяця за кілька секунд

<img src="screens/03-main-entry.png" width="260"> <img src="screens/04-main-feed.png" width="260"> <img src="screens/05-main-feed-scrolled.png" width="260">

[src/app/(tabs)/index.tsx](<../src/app/(tabs)/index.tsx>) · спека `main-screen`

Зверху — **місячний статус**: «Залишилось у вересні» головною цифрою і «Витрачено» під ним, по
кожній валюті окремо, з тими самими числами, які показує «Місяць» (тап по картці туди й веде).
Якщо за місяць ще немає доходу, там же стоїть речення, чому «залишилось» від'ємне. Під рискою —
вторинний рядок **«На рахунках …»** з приблизною гривнею; тап веде на «Рахунки».

Далі — **«Потребує уваги»**, і тільки якщо є що: скільки транзакцій без категорії (тап → «Транзакції»)
і чернетки зі сповіщень банків, які підтверджують або відхиляють просто тут. Немає ні того, ні
іншого — секції немає взагалі, разом із заголовком.

Нижче — стрічка **останніх 5** транзакцій і кнопка **«Усі ›»**. У стрічці видно все, що застосунок
вважає важливим:

- **«Без категорії»** підсвічено крапкою і має кнопку «Обрати категорію» — категоризація в один тап;
- дохід — зеленим, переказ — рядком `рахунок → рахунок`, коригування — зі знаком;
- категорія, що перевищила свій ліміт цього місяця, — червоним.

Тап по транзакції відкриває редагування (§3.9).

Форми на Головному немає: записує **«+»** у правому нижньому куті — окремий екран
[transaction/new.tsx](<../src/app/transaction/new.tsx>) з тим самим типом, рахунком, сумою, датою,
недавніми категоріями й описом, що були тут раніше. За замовчуванням це **витрата** — «будь-яка
транзакція є витратою, доки її явно не типізували інакше». Після запису екран лишається відкритим
з підтвердженням і порожньою сумою, щоб наступну витрату дня можна було записати одразу.

### 3.3. Місяць — куди пішли гроші і скільки лишилось

<img src="screens/06-month.png" width="260"> <img src="screens/07-month-current.png" width="260"> <img src="screens/08-category-month.png" width="260">

[src/app/(tabs)/month.tsx](<../src/app/(tabs)/month.tsx>) · спеки `month-screen`, `monthly-picture`

П'ять чисел місяця плюс дохід, окремою карткою на кожну валюту. Ліворуч — серпень 2026:
`Позичено −4000,00` — це повернений борг, тому число від'ємне; `Відкладено 5000,00` — переказ у
банку; `Інвестовано 8000,00` — переказ на військові облігації. Посередині — поточний місяць, у
якому минув один день: стрілки ← → гортають місяці.

Під числами — **витрачено за категоріями**: смужка кожного рядка масштабована до найбільшої
категорії місяця, категорія понад ліміт — червона. Тап по рядку відкриває цю категорію за цей
місяць (праворуч) з підписом, на скільки саме перевищено ліміт.

### 3.4. Рахунки — де лежать гроші

<img src="screens/09-accounts.png" width="260"> <img src="screens/10-account.png" width="260"> <img src="screens/11-account-new.png" width="260">

[src/app/(tabs)/accounts.tsx](<../src/app/(tabs)/accounts.tsx>),
[account/&#91;id&#93;.tsx](<../src/app/account/[id].tsx>) · спеки `accounts-screen`, `accounts`

Рахунки згруповані за видом, у кожної групи — власний підсумок по валютах. **Баланс завжди
розрахунковий**: початковий залишок плюс усі транзакції. Балансів, які не пояснюються
транзакціями, не існує. Для рахунку, зв'язаного з monobank, тут же поруч показується останній
відомий **баланс банку** — поруч, а не замість: банк ніколи не перезаписує розрахункове число.

Тап по рахунку відкриває його рухи (посередині) з полем **«Звірити»**: власник вводить фактичний
залишок, і застосунок створює транзакцію-коригування на різницю.

Праворуч — форма нового рахунку: назва, вид, валюта, початковий залишок. Вид і валюта після
створення не змінюються (це змінило б сенс усієї історії рахунку); назву і початковий залишок
редагувати можна. Рахунки не видаляються — лише архівуються.

### 3.5. Звіти — історія та цілі

<img src="screens/12-reports.png" width="260"> <img src="screens/13-reports-category-goals.png" width="260">

[src/app/(tabs)/reports.tsx](<../src/app/(tabs)/reports.tsx>) · спеки `reports-screen`, `reports`

Три секції:

1. **Історія за місяцями** — витрачено / дохід / інвестовано за весь час, стовпчиками. Кожен графік
   називає свою шкалу (максимум і нуль), а один місяць — вибраний — розписано числами повністю,
   бо стовпчик без числа нічого не доводить.
2. **Одна категорія за місяцями** — обрана категорія по всій історії.
3. **Цілі** — прогрес як «скільки є / скільки треба» і дата.

Перемикач валюти вгорі: кожна валюта читається окремо, нічого не конвертується.

### 3.6. AI-аналіз — попросити асистента пояснити числа

<img src="screens/13a-ai-analysis.png" width="260"> <img src="screens/13b-ai-analysis-actions.png" width="260">

[src/app/ai-analysis.tsx](../src/app/ai-analysis.tsx) · спеки `ai-analysis-screen`,
`ai-analysis-package`, `ai-analysis-share`

Відкривається зі «Звітів». Числа рахує застосунок — асистент лише читає їх уголос: що змінилося,
які категорії зросли, що виглядає необов'язковим. Він нічого не рахує, нічого не змінює і жодного
числа в застосунку не бачить, крім тих, що вже пораховані.

Власник обирає **вид** («Місячна картина»), **період** («Цей місяць», 3, 6, 12 місяців або свій
діапазон цілих місяців) і два перемикачі, обидва **вимкнені** щоразу, коли екран відкривається:
«Продавці» (описи транзакцій — текст банку) і «Окремі транзакції». Агрегати — місячна картина,
категорії, тренди, ліміти й цілі — включені завжди.

**Що з телефона не виходить ніколи:** жоден ідентифікатор, жодна назва рахунку, токен monobank,
баланс банку, текст перехоплених сповіщень, чернетки, відстежувані застосунки і бекап. Описи й
окремі транзакції виходять лише тоді, коли власник увімкнув їх для цього одного запуску, і це
ніде не запам'ятовується.

**Що тримає файл для аналізу:** інструкції асистентові (українською: користуйся лише цими даними,
нічого не вигадуй, нічого не перераховуй, не поєднуй валюти, не прогнозуй), контекст із
визначеннями шести чисел і п'яти розрізнень зі словника, читабельний підсумок і сам пакет як JSON.

Перед тим як щось піде кудись, екран показує **прев'ю того самого пакета**, який і буде передано:
скільки місяців, транзакцій, категорій, які валюти, продавці так/ні, окремі транзакції так/ні і
приблизний розмір у КБ — плюс «Показати файл», який показує текст цілком. Нічого не залишає
телефон, доки власник не натисне «Поділитися з AI»: тоді відкривається **системний вибір
застосунків**, і застосунок обирає власник. Телефон не каже, що власник там зробив, тому екран
каже рівно «Файл передано системі» і нічого більше. Поруч завжди є «Скопіювати» — той самий текст
у буфер.

### 3.9. Редагування транзакції

<img src="screens/15-transaction-edit.png" width="260">

[transaction/&#91;id&#93;.tsx](<../src/app/transaction/[id].tsx>)

Та сама форма, що й швидке додавання, плюс видалення. Зміна типу (витрата → переказ або
інвестиція) — штатна щоденна дія, а не виняток: саме так імпортована «витрата» стає переказом на
банку.

Тут же — **фіскальний чек**. Витрата чи повернення без чека пропонує «Сканувати QR чека»
([transaction/scan.tsx](../src/app/transaction/scan.tsx)) — помітніше для витрати в засіяній
категорії «Продукти», тихіше в інших. Сканер читає QR з паперового чека, застосунок питає
податкову за реквізитами, показує позиції з сумою і чекає рішення власника; збігу сум немає —
питає ще раз, перш ніж прикріпити. Транзакція, яка вже має чек, показує рядок «Фіскальний чек · N
позицій · сума» і веде до списку позицій ([transaction/receipt.tsx](../src/app/transaction/receipt.tsx)),
де чек можна відкріпити. Переказ, дохід і коригування сканування не пропонують — але чек, який
вони отримали до зміни типу, лишається видимим.

Чек — це **деталь під транзакцією, а не гроші**: жоден розрахунковий баланс, жодне число місячної
картини, жоден ліміт, ціль чи звіт від нього не змінюються, і жодна позиція не стає транзакцією.

## 4. Налаштування по розділах

### 4.1. Категорії, Джерела

<img src="screens/17-categories.png" width="260">

[manage/categories.tsx](../src/app/manage/categories.tsx),
[manage/sources.tsx](../src/app/manage/sources.tsx) · спека `categories`

Плоскі списки з стартовим набором власника (його ж категорії з Saldo, ієрархія розплющена).
Створення, перейменування, архівація; **видалення немає** — архівна категорія лишається на своїх
транзакціях, але більше не пропонується. Службові рядки («Без категорії», «Комісія»,
«Коригування», «Відсотки», «Без джерела») не перейменовуються і не архівуються — застосунок сам
на них посилається.

### 4.2. Правила

<img src="screens/18-rules.png" width="260">

[manage/rules.tsx](../src/app/manage/rules.tsx) · спека `categorisation-rules`

«Продавець і/або MCC → категорія». Застосовуються до імпортованих транзакцій; збіг
детермінований, найточніше правило виграє. Сходинки точності: продавець **і** MCC → лише
продавець → лише MCC; за однакової точності виграє довший шаблон продавця, потім новіше правило.
Правило без жодного критерію не створюється.

### 4.3. Ліміти і Цілі

<img src="screens/19-limits.png" width="260"> <img src="screens/20-goals.png" width="260">

[manage/limits.tsx](../src/app/manage/limits.tsx),
[manage/goals.tsx](../src/app/manage/goals.tsx) · спеки `limits`, `goals`

Ліміт — не більше одного на категорію, у своїй валюті; порівнюється з витраченим за місяць у тій
самій валюті. Нічого не блокує і нічого не надсилає — лише фарбує червоним.

Ціль — назва, сума, дата і один рахунок. Прогрес **читається** з розрахункового балансу цього
рахунку, а не вводиться руками, тому не може розійтися зі збереженою правдою.

### 4.4. monobank

<img src="screens/21-monobank.png" width="260">

[manage/monobank.tsx](../src/app/manage/monobank.tsx) · спеки `monobank-sync-screen`, `monobank-sync`

Токен зберігається лише в захищеному сховищі телефона (`expo-secure-store`): він не потрапляє ні
в базу, ні в бекап, ні в лог, і показати його вдруге неможливо. Кнопка «Отримати токен» відкриває
сторінку monobank і після повернення підставляє токен з буфера.

Далі — список рахунків monobank, зв'язування кожного з рахунком застосунку **тієї самої валюти**,
і синхронізація: кожен зв'язаний рахунок продовжує з власного збереженого курсора, один елемент
виписки імпортується **щонайбільше один раз, назавжди**. Відключення monobank ніколи не видаляє
історію грошей.

### 4.5. Сповіщення банків

<img src="screens/22-bank-notifications.png" width="260"> <img src="screens/23-bank-notifications-add.png" width="260">

[manage/notifications.tsx](../src/app/manage/notifications.tsx) · спеки `bank-notifications*`

Як автоматично ловляться банки, у яких немає API. Власник дає Android-дозвіл на читання
сповіщень і додає **відстежувані застосунки**: один застосунок → рівно один рахунок. Сповіщення
всіх інших застосунків не читаються взагалі; застосунки monobank відстежувати заборонено — mono
вже приходить через API з реальними ідентифікаторами, і другий, слабший шлях міг би лише
наробити дублікатів.

Розібране сповіщення стає **чернеткою** на Головному: вона нічого не рухає, доки власник її не
підтвердить. Правило може підтвердити розібрану витрату автоматично. Нічого з прочитаного не
залишає телефон і не потрапляє в бекап.

### 4.6. Нагадування

<img src="screens/24-reminders.png" width="260">

[manage/reminders.tsx](../src/app/manage/reminders.tsx)

Застосунок надсилає рівно два види сповіщень: одне щоденне нагадування записати витрати (якщо
ввімкнути, у вибраний час) і сповіщення про збій, коли те, що застосунок робив сам, не вдалося.
У жодному з них немає ні суми, ні рахунку, ні категорії, ні тексту банківського сповіщення.
Віддалених push-сповіщень немає — усе планує сам телефон.

### 4.7. Бекап

<img src="screens/25-backup.png" width="260">

[manage/backup.tsx](../src/app/manage/backup.tsx)

Один файл з усіма рахунками, транзакціями, списками та налаштуваннями. **Не зашифрований** — хто

### 4.8. Імпорт Saldo

<img src="screens/26-saldo-import-map.png" width="260"> <img src="screens/27-saldo-import-report.png" width="260"> <img src="screens/28-saldo-import-done.png" width="260">

[manage/saldo-import.tsx](../src/app/manage/saldo-import.tsx) · спеки `saldo-import-screen`, `saldo-import`

Разовий переїзд з попереднього застосунку. Майстер показує, що саме він зробить, **перш ніж
зробити хоч що-небудь**:

1. **Рахунки** — кожна пара (рахунок Saldo, валюта) стає рахунком; вид можна змінити
   (тут «Банка на відпустку» переведено у «Накопичувальні»), а два рахунки Saldo, що насправді
   одна картка, — об'єднати.
2. **Нові категорії та джерела** — те, чого ще немає за назвою; кожен рядок можна перенаправити
   на наявний.
3. **Звірка** — по кожному рахунку показано баланс за Saldo і баланс за планом імпорту та їхню
   різницю. Транзакція, якої імпорт не розпізнав, потрапляє у звіт, а не зникає мовчки.
4. **Імпорт** — увесь план записується як одне ціле або не записується взагалі; повторний імпорт
   попереджає, що подвоїть історію.

### 4.9. Репорти про помилки

[manage/bug-reports/index.tsx](../src/app/manage/bug-reports/index.tsx) · спеки `bug-report`,
`bug-report-screen`

Поки застосунок молодий, а тестує його одна людина на одному телефоні, помилка, яку побачили
ввечері, до ранку лишається однією фразою «щось не записалося». Цей розділ дає їй форму.

**Журнал.** Застосунок веде власний обмежений запис того, що робив: кожен відкритий екран (за
маршрутом), кожну дію, яка не вдалася — з точним текстом, який побачив власник, — кожне підняте
чи зняте сповіщення про збій і кожен збій з повідомленням і стеком. Останні 500 записів, старіші
випадають. У журналі ніколи немає ні суми, ні назви, ні опису, ні тексту банківського сповіщення,
ні токена monobank. Єдиний виняток названо прямо: якщо власна відмова застосунку цитує те, що
власник щойно ввів («Рахунок «Картка» вже існує»), цитата лишається в тому одному записі — бо
відтворити помилку без точного тексту не вийде.

**Репорт.** Власник пише три рядки — що робив (обов'язково), що сталося, чого очікував, — а
застосунок сам додає версію і збірку (короткий коміт і чи було дерево чистим), платформу,
пристрій, кількість застосованих міграцій, маршрут екрана, момент, увесь журнал, ту помилку чи
збій, з якого все почалося, і кількості того, що на телефоні, — самі числа. Скріншоти власник
додає до вже збереженого репорта.

**Звідки він береться.** Будь-який діалог з відмовою пропонує, поруч із «Закрити», «Повідомити
про помилку» — і форма відкривається з тією відмовою вже прикріпленою. Якщо екран узагалі впав,
замість мертвого застосунку показується запасний екран українською з текстом помилки, «Повідомити
про помилку» і «Повернутися». А без жодного приводу репорт заводиться просто тут, у розділі.

**Що звідси виходить.** Нічого — доки власник не скаже. Збережений репорт показано **цілим**: те,
що на екрані, і є те, що піде. «Скопіювати» кладе цей текст у буфер; «Передати» віддає один
Markdown-файл (зі скріншотами всередині) системному вибору застосунків — далі це вже чат із
Claude Code. Жодного сервера, жодної аналітики, жодного автоматичного відсилання. У бекап
репорти і журнал не потрапляють ніколи, і відновлення їх не чіпає.

## 5. Як влаштовано всередині

### 5.1. Шари

```
src/domain/     чистий TypeScript: гроші, рахунки, транзакції, місячна картина, ліміти, цілі,
                правила, звіти. Нічого не знає про React, базу, мережу і платформу.
src/ui/         чиста логіка екранів без жодного імпорту React: розбір суми, підписи, групування,
                стан майстрів. Саме тут перевіряється те, що виглядає як «поведінка екрана».
src/app/        expo-router: (tabs)/ — п'ять вкладок; transaction/, category/, account/,
                transactions, ai-analysis, manage/, onboarding — екрани поверх вкладок.
src/components/ спільні примітиви UI (форми, поверхні, теми, таби).
src/db/         Drizzle: schema.ts + репозиторії; drizzle/ — міграції (0000…0011).
src/platform/   порти до пристрою і їхні тестові двійники; *-device.ts — нативні адаптери.
src/monobank/   API, розбір виписки, координатор синхронізації, курс.
src/notifications/ розбір банківських сповіщень і життєвий цикл чернеток.
src/saldo/      розбір CSV, інтерпретація в транзакції, звірка балансів.
src/fiscal/     фіскальні чеки: читання QR, порт пошуку в податковій і його адаптер, декодування
                windows-1251, два діалекти документа (ПРРО і класичний РРО). Чистий TypeScript.
src/analysis/   пакет для аналізу і файл для аналізу: період, місяці, категорії, тренди, цілі,
                деталі, точний десятковий текст і базисні пункти, текст промпта і рендер файлу.
                Чистий TypeScript; не знає ні про базу, ні про React, ні про мережу.
src/backup/     формат бекапу і канонізація.
src/reminders/  розклад нагадувань і тексти сповіщень.
modules/notification-capture/   локальний Expo-модуль на Kotlin: Android NotificationListener.
```

Правило, яке тримає все це разом: **`npm run verify` ніколи не завантажує нативний модуль і не
запускає React Native**. Тому кожна взаємодія з телефоном — це *порт* (тип + тестовий двійник) в
`src/platform/`, а нативний адаптер лежить у сусідньому файлі, який порт не імпортує. Помилки —
це **значення**, а не винятки: «немає дозволу», «немає такої можливості на цій платформі»,
«користувач скасував» — це відповіді, які екран показує словами власника.

### 5.2. Дані

Одна база SQLite (`cap1tal.db`) у приватному сховищі застосунку, 20 таблиць:

| Група | Таблиці |
|---|---|
| гроші | `accounts`, `transactions` |
| списки | `categories`, `sources`, `rules` |
| бюджет | `category_limits`, `goals` |
| monobank | `monobank_accounts`, `monobank_links`, `monobank_imported_items`, `monobank_rates` |
| сповіщення | `notification_watches`, `notification_fingerprints`, `notification_drafts` |
| чеки | `fiscal_receipts`, `receipt_items` |
| службове | `saldo_import`, `daily_reminder`, `alerts`, `entry_defaults` |

Правила бази ([.claude/rules/database.md](../.claude/rules/database.md)):

- **гроші — цілі мінорні одиниці плюс код валюти**. Ніколи не float, ніколи не сума різних валют;
- закомічена міграція **незмінна**: зміна схеми = нова міграція + тест;
- міграції застосовуються рівно в одному місці — кореневий layout, до першого читання екраном;
- зовнішні ключі увімкнені, посилання на рахунок — `onDelete: restrict` (рахунки архівуються).

### 5.3. Куди тече одна транзакція

```
                    ручний ввід («+» → форма)
                                 │
   monobank API ──► sync ────────┤
                                 ├──► src/domain/transaction ──► src/db/transactions-repo
   сповіщення банку ──► parse ──►│         (типи, інваріанти)          (SQLite)
        (чернетка → підтвердження)                                        │
   CSV Saldo ──► parse ──► interpret ──► план ─────────────────────────────┘
                                                                          │
                             src/domain/monthly-picture ◄─────────────────┤
                             src/domain/reports        ◄─────────────────┤
                             src/domain/account        ◄─────────────────┘
                                       │
                              екрани Місяць / Звіти / Рахунки
```

Жодне число на екрані не зберігається — баланси, місячна картина, прогрес цілі й перевищення
ліміту **обчислюються** з транзакцій щоразу.

### 5.4. Робочий цикл і перевірка

Робота ведеться специфікаціями (OpenSpec). Коротко:

```
/opsx:propose  →  spec-reviewer  →  /opsx:apply  →  npm run verify  →  diff-reviewer
       →  коміт  →  димовий тест на емуляторі  →  /opsx:archive
```

- `npm run verify` = `openspec validate` → lint → typecheck → тести. Менше хвилини, без емулятора
  і без нативної збірки. Це **єдиний** критерій «готово»; хук відмовляє зробити коміт, якщо дерево
  не збігається з останнім зеленим прогоном.
- 89 файлів тестів (1479 тестів) лежать поруч із кодом (`*.test.ts`, Vitest). База в тестах —
  `better-sqlite3` поверх **тих самих** закомічених міграцій.
- `verify` не покриває нативний код. Усе, що стосується поведінки екрана, перевіряється на
  емуляторі: `scripts/android.sh up | shot | tap | text` ([правила](../.claude/rules/android.md)).
  Саме цим інструментом зроблено скріншоти в цьому файлі.

## 7. Свідомо поза межами v1

Це не «ще не зробили», а **вирішено не робити** (§14 візії). Пропозиція нової фічі, яка потрапляє
в цей список, потребує спершу зміни візії:

1. спільні дані, кілька користувачів, жива двостороння синхронізація між пристроями;
2. позиції та інструменти інвестицій, автоматичні ціни (лише ручна поточна вартість рахунку);
3. деталі позик: терміни, ставки, графіки платежів;
4. «гроші в дорозі» як окремий стан;
5. розділення однієї покупки на кілька категорій;
6. регулярні та заплановані транзакції;
7. інтеграції з банками поза monobank API і розбором сповіщень (жодного SMS);
8. ієрархія категорій і теги;
9. хмарні сервіси, крім опційного Google Drive для бекапу;
10. прогнози («такими темпами лишиться X»);
11. перенесення транзакції в інший місяць;
12. платежі й перекази **з** застосунку — він записує гроші, він їх не рухає;
13. загальний місячний ліміт (лише по категоріях);
14. віддалені push-сповіщення;
15. збірка під iOS — але ніщо в моделі не має їй заважати.

## 8. Як обговорювати нову фічу

Корисна послідовність питань — вона ж підказує, куди ляже код:

1. **На яке з двох питань візії це працює** — «куди пішли гроші» чи «скільки можна витратити»?
   Якщо ні на яке, це, найімовірніше, §7.
2. **Чи є для цього слово в [glossary.md](glossary.md)?** Нових синонімів не вигадуємо; якщо слова
   немає — його треба додати в глосарій, і це частина зміни.
3. **Це нова поведінка чи новий екран для наявної?** Нова поведінка потребує вимоги в
   `openspec/specs/<capability>/` — жодної зміни поведінки без специфікації, яка її описує.
4. **Де вона живе за шарами?** Чисте правило → `src/domain/`; логіка екрана → `src/ui/`;
   нове сховище → міграція + репозиторій; нова взаємодія з телефоном → **порт** у `src/platform/`
   з тестовим двійником.
5. **Чи торкається вона грошей?** Тоді: цілі мінорні одиниці, одна валюта на арифметичну операцію,
   і жодного балансу, який не пояснюється транзакціями.
6. **Як це перевіряється?** Якщо не запуском `npm run verify`, то яким сценарієм на емуляторі.

Далі — звичайний цикл: `/opsx:propose` → `spec-reviewer` → `/opsx:apply`.
